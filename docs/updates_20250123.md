## 8. API 接口统一为 SSE 流式输出

### 8.1 核心变更
将所有 API 接口统一为 Server-Sent Events (SSE) 流式输出，提供一致的实时反馈体验。

#### 统一流式端点
- **新增端点**：`POST /stream`
- **支持的操作类型**：
  - `chat` - 聊天对话
  - `generate` - 生成完整简历
  - `history` - 获取对话历史
  - `reasoning_status` - 获取背景推理状态（仅 Dual-Track）
  - `token_stats` - 获取 token 统计
  - `token_summary` - 获取 token 摘要

#### SSE 事件类型
- `status` - 状态更新（处理中、工具调用等）
- `partial` - 部分内容（流式输出）
- `final` - 最终结果
- `error` - 错误信息

### 8.2 Schema 更新
- **新增 `StreamRequest` 模型**（`src/schema/request.py`）：
  ```python
  class StreamRequest(BaseModel):
      action: Literal["chat", "generate", "history", "reasoning_status", "token_stats", "token_summary"]
      session_id: Optional[str] = "default"
      agent_type: Optional[AgentType] = AgentType.PLANNER_WORKER
      message: Optional[str] = None  # chat 操作需要
      limit: Optional[int] = 50  # history 操作需要
      # token_stats 相关参数
      token_agent_type: Optional[str] = None
      token_model: Optional[str] = None
      start_date: Optional[str] = None
      end_date: Optional[str] = None
      group_by: Optional[str] = None
  ```

### 8.3 API 路由重构
- **统一路由实现**（`src/api/routes.py`）：
  - 所有操作通过 `POST /stream` 端点处理
  - 使用 `EventSourceResponse` 返回 SSE 流
  - 工具调用回调通过队列收集事件，实时发送 SSE 事件
  - 支持两种工具调用回调方式（三个参数和两个参数）

### 8.4 前端更新
- **统一使用 SSE 流式接口**：
  - 使用 `fetch API + ReadableStream` 处理 POST SSE 请求（EventSource 仅支持 GET）
  - 更新 `sendMessage()` 函数，统一调用 `startChatStream()`
  - 更新 `loadSessionHistory()` 和 `fetchSessionTokenStats()` 使用 SSE
  - 实时显示处理状态和工具调用信息

### 8.5 向后兼容
- **保留旧接口**（标记为已废弃）：
  - `POST /chat` → 提示使用 `POST /stream`，`action=chat`
  - `GET /chat/stream` → 提示使用 `POST /stream`，`action=chat`
  - `POST /resume/generate` → 提示使用 `POST /stream`，`action=generate`
  - `GET /reasoning-status/{session_id}` → 提示使用 `POST /stream`，`action=reasoning_status`
  - `GET /history/{session_id}` → 提示使用 `POST /stream`，`action=history`
  - `GET /token/*` → 提示使用 `POST /stream`，`action=token_stats` 或 `token_summary`

### 8.6 使用示例

#### JavaScript 客户端
```javascript
// 聊天对话
const response = await fetch('/stream', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({
        action: 'chat',
        message: '我在字节跳动做过后端开发',
        session_id: 'my_session',
        agent_type: 'planner_worker'
    })
});

const reader = response.body.getReader();
const decoder = new TextDecoder();
let buffer = '';

while (true) {
    const { done, value } = await reader.read();
    if (done) break;
    
    buffer += decoder.decode(value, { stream: true });
    const lines = buffer.split('\n');
    buffer = lines.pop() || '';
    
    for (const line of lines) {
        if (line.startsWith('data: ')) {
            const data = JSON.parse(line.slice(6));
            console.log('SSE Event:', data);
            // 处理不同类型的事件
            if (data.type === 'status') {
                // 显示状态更新
            } else if (data.type === 'final') {
                // 显示最终结果
            }
        }
    }
}
```

#### Python 客户端
```python
import requests
import json

response = requests.post(
    'http://localhost:8000/stream',
    json={
        'action': 'chat',
        'message': '我在字节跳动做过后端开发',
        'session_id': 'my_session',
        'agent_type': 'planner_worker'
    },
    stream=True
)

for line in response.iter_lines():
    if line.startswith(b'data: '):
        data = json.loads(line[6:].decode('utf-8'))
        print(f"Event Type: {data['type']}")
        if data['type'] == 'final':
            print(f"Response: {data['content']}")
```

### 8.7 优势
1. **统一的接口体验**：所有操作都通过相同的 SSE 流式接口，提供一致的实时反馈
2. **实时状态更新**：可以实时显示处理进度、工具调用状态等
3. **更好的用户体验**：用户可以看到系统正在做什么，而不是等待最终结果
4. **简化前端代码**：统一的接口减少了前端需要处理的端点数量
5. **易于扩展**：新增操作类型只需在 `action` 参数中添加新值

### 8.8 技术细节
- **工具调用回调优化**：
  - 使用 `asyncio.Queue` 收集工具调用事件
  - 在后台任务运行期间实时处理队列中的事件
  - 支持两种回调方式（三个参数：intent, tool_name, tool_args；两个参数：tool_name, tool_args）
  
- **SSE 事件格式**：
  ```
  data: {"type": "status", "content": "正在处理..."}
  data: {"type": "final", "content": "处理完成", "session_id": "...", ...}
  ```

### 8.9 注意事项
- EventSource API 仅支持 GET 请求，因此使用 `fetch API + ReadableStream` 处理 POST SSE 请求
- 所有操作都返回流式响应，即使是简单的查询操作（如获取历史）
- 旧接口仍然可用但已标记为废弃，建议尽快迁移到新接口

## 9. 架构性能对比分析

为了对比不同架构的响应速度、聪明度和时间消耗，已创建详细的对比分析文档：

📊 **[架构性能对比报告](./architecture_comparison_20250123.md)**

### 对比要点总结

#### 响应速度
- **Planner-Worker**：~3-7秒（用户需等待完整处理）
- **Dual-Track**：~0.5-1秒（快速响应，后台深度推理）
- **优势**：Dual-Track 用户感知等待时间减少 70-85%

#### 聪明度（推理质量）
- **Planner-Worker**：中等（同步推理，问题可能重复）
- **Dual-Track**：高（深度推理，问题去重，支持对话历史）
- **优势**：Dual-Track 在问题生成质量和对话理解方面更优

#### 时间消耗
- **Planner-Worker**：用户等待时间 = 完整处理时间（~3-7秒）
- **Dual-Track**：用户等待时间（~0.5-1秒）<< 完整处理时间（~4-7秒）
- **优势**：Dual-Track 虽然总处理时间相当，但用户感知的响应速度更快

#### 适用场景
- **生产环境**：推荐 Dual-Track 架构（响应快、质量高）
- **开发测试**：推荐 Planner-Worker 架构（流程清晰、易调试）

详细对比数据和分析请参考：[架构性能对比报告](./architecture_comparison_20250123.md)
